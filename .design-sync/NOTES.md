# fitmetrik-web design-sync notes

## Shape and scope

No Storybook, no shipped `dist/` — this is a Next.js app, not a published
component package. Auto-detection would default to scanning the entire
`src/` tree for PascalCase exports (synth-entry mode), which would try to
bundle route pages, Server Actions, `mongoose`, and Supabase server clients
into a browser IIFE. That breaks.

**Fix**: `cfg.entry` pins the bundle to a hand-written `.design-sync/entry.mjs`
that re-exports only the scoped components. `cfg.componentSrcMap` pins each
component's exact source path (bypassing fuzzy-find and the automatic
full-`src/`-scan fallback, which only triggers when the name list would
otherwise be empty).

**First-sync scope** (user-approved, see AskUserQuestion in this session):
the 8 atoms in `src/components/ui/` (Alert, Badge, Button, Card, Input,
Modal, StatusPill, Table — Table's file also exports TableHead/TableRow/
TableCell as siblings, all included) plus 4 reusable feature components:
MetricCard, SummaryCard, PlanCard, TablePagination. The other ~32 components
in the repo (page orchestrators, modals wired to Server Actions, etc.) are
deliberately NOT synced — they don't render standalone and a broken card is
worse than no card. They can be added incrementally on a future re-sync via
`componentSrcMap`/`dtsPropsFor` additions.

## No shipped `.d.ts` → hand-written `dtsPropsFor` for every component

`dts.mjs` extracts props from a package's shipped `.d.ts` tree
(`pkgJson.types`/`typings`), which doesn't exist here. Without
`cfg.dtsPropsFor`, every component would get an empty Props interface.
All 15 exports (12 components + 3 Table siblings) have hand-written prop
bodies in config, transcribed from their actual `interface`/type declarations
in source as of this sync. **Re-sync risk**: if a component's real props
change, the hand-written body silently drifts — re-check it against source
when re-syncing, especially for Button/Input (which extend
`React.*HTMLAttributes` — only the commonly-used attributes were inlined,
not the full extended surface) and Modal (`initialFocusRef` was dropped from
the emitted props — a `RefObject` type isn't useful to a design agent anyway).

## CSS: `cssEntry` is a compiled artifact, not the repo's source file

`src/app/globals.css` starts with `@import "tailwindcss";` and a Tailwind v4
`@theme` block — esbuild cannot process either. `cfg.cssEntry` points at
`.design-sync/.cache/tailwind-build.css`, generated by `cfg.buildCmd`
(`npx @tailwindcss/cli@4.3.2 -i src/app/globals.css -o .design-sync/.cache/tailwind-build.css`).
**This must be re-run before every rebuild** — `.design-sync/.cache/` is
gitignored, so a fresh clone or a stale cache will have an empty/missing
compiled CSS and components render unstyled. The driver/resync flow should
run `cfg.buildCmd` first; if running the converter manually, run it by hand
first too.

Used Tailwind's own CLI (pinned to the installed `tailwindcss@4.3.2`) against
content-auto-detected across the whole repo rather than `yarn build`'s
production CSS extraction — faster, avoids Next.js build-time env/DB
dependencies, and vendor prefixing (autoprefixer, used in the app's real
`postcss.config.mjs`) doesn't matter for a Chromium-rendered preview.

## Fonts

Only Manrope is self-hosted (`@fontsource/manrope/{400,500,600,700,800}.css`,
imported directly in `src/app/layout.tsx`). `cfg.extraFonts` points at those
same files so design-sync copies the font files into `fonts/`.

The `--font-display: "Public Sans"` and `--font-body`/`--font-label: "Inter"`
theme tokens in `globals.css` are **not backed by any shipped font** anywhere
in the repo (no `next/font`, no `@fontsource` package for either family) —
verified none of the scoped components use the `font-display`/`font-body`/
`font-label` Tailwind utilities, so this sync never hits `[FONT_MISSING]`.
If a future-synced component uses those utilities, this needs a real
decision (source the fonts, or treat as a known fallback-font gap) — don't
silently wire `extraFonts` to something that doesn't exist.

## Confirmed-working items (hypotheses tested during the self-heal loop)

- `Alert.tsx` imports `./Alert.module.css` (a CSS Module). esbuild's default
  CSS loader (no override — see `lib/bundle.mjs`'s comment) does NOT
  generate a CSS-Modules classname-mapping proxy object in general, which
  raised a concern that `styles.error`/`styles.success`/`styles.info` would
  resolve to `undefined` at runtime. **Tested via the render check and full-
  resolution screenshots: all three Alert variants render correctly styled**
  (distinct red/blue/green tinted boxes). Not an issue in practice for this
  component — no further action needed.
- `Modal`'s `useSyncExternalStore` + `createPortal(..., document.body)`
  renders correctly in headless chromium with `open: true` in the authored
  preview. No issue.
- `Table`/`TableHead`/`TableRow`/`TableCell` have no background of their
  own — first authoring attempt composed them bare and the text rendered
  nearly illegible (light `--color-on-background` text on the design-sync
  preview harness's white page, instead of the app's actual dark `<body>`).
  **Fix**: in the real app `Table` is always composed inside
  `<Card padding="none">` (see `ClientRosterTable.tsx`) — wrapped all four
  Table-family previews in `Card` to match real usage. This is a real
  usage-pattern fact, not a cosmetic preview hack: Table was never designed
  to stand alone outside a Card.

## Known, deliberate gap: SummaryCard ships as a floor card only

`SummaryCard.tsx` hardcodes a `material-symbols-outlined` icon span
(`directions_run`) — not a prop, baked into the component's own JSX. Material
Symbols Outlined is loaded by the real app via a remote Google Fonts
`<link>` tag in `layout.tsx`, not bundled.

Tried to resolve properly (per the skill's "resolve it, don't rationalize it
away" guidance): downloaded the actual woff2 Google serves for this family —
**1.1MB** for the full variable font, to support rendering ONE hardcoded
decorative icon on ONE non-core, optional component. Judged not
proportionate and removed the download rather than ship it.

Marked `"Material Symbols"` in `cfg.runtimeFontPrefixes` (honest signal:
loads at runtime from a font service, like the real app, not shipped) and
**deliberately left `SummaryCard` unauthored** (no `.design-sync/previews/
SummaryCard.tsx`) rather than ship an authored preview with a known-broken
icon graded `needs-work` forever — the floor card is the honest state here,
not a failure. `SummaryCard`'s bundle entry, `.d.ts`, and `.prompt.md` are
all still fully functional; only the rich preview is withheld.

**To revisit**: if SummaryCard becomes more central to this design system,
either (a) subset the Material Symbols woff2 to just the glyphs actually
used (uncertain whether Google's `text=` subsetting param reliably preserves
the ligature substitution these icons depend on — untested), or (b) accept
the 1.1MB cost and ship it via `cfg.extraFonts`.

## Re-sync risks

- The hand-written `.design-sync/entry.mjs` and `componentSrcMap` do not
  auto-discover new components — adding one to the synced set means editing
  both files by hand (add the export to `entry.mjs`, add the path to
  `componentSrcMap`, add props to `dtsPropsFor`).
- `cfg.buildCmd`'s Tailwind CLI compile is pinned to `4.3.2` — if the repo's
  `tailwindcss` dependency is upgraded, bump the pin or it may emit utilities
  the installed engine doesn't recognize (or vice versa).
- `dtsPropsFor` bodies are hand-transcribed and will NOT auto-update if the
  real component props change — see the dedicated section above.
